# Chain adapter boundary

`index.ts` exports `deriveGoalBinding`, `createChainService`, `planGoalStep`, `assertPlanUsable`, `readGoalState` and `reconcileGoalStep`. The module is read-only: it does not import wallet keys, sign, submit transactions, or write application metadata. `ReadOnlyRpc` refuses broadcast methods. The API repository owns authentication, durable step IDs, the original transaction hash and receipt uniqueness.

Provisioning uses a server-reserved random goal ID and verified linked wallet addresses. `deriveGoalBinding` derives the Solana goal/cash PDAs and canonical participants. Solana plus one to three supported EVM testnets is required. Each user signs `create-vault` on the selected EVM networks. The verifier discovers the **actual** vault from the canonical router's `VaultCreated` event and checks its independent configuration leaf and immutable provenance. It never reserves a predicted CREATE address. Only after all selected creation receipts are verified can the user sign Solana `initialize`.

The operator may coordinate authenticated registration, reports, readiness and commitment. User funds cannot deposit until every selected participant is registered and linked. User preparation and abort remain owner-signed Solana actions. EVM approval is a separate exact-amount step. Deposits and claims are never operator actions. The permissionless worker and its admission/fee policy live under `contracts/keeper`; this adapter does not grant it wallet ownership. The current operator registry has a finite capacity and must admit a new goal before promising coordination.

Every plan has a canonical JSON fingerprint that survives PostgreSQL JSONB key ordering. The verifier also reconstructs the canonical method/program/accounts, so a recomputed fingerprint cannot turn another instruction into an authorized goal action. Solana plans contain an unsigned v0 wire with zero signatures; direct signing wallets must preserve its exact message. Legacy EVM plans retain the direct-owner verifier. New `gasPayment: privy-testnet` plans use a separate ERC-4337 v0.7 owner-operation verifier for canonical Alchemy and Kernel v3.3 EIP-7702 delegates. Sponsorship is selected by the API from the authoritative linked Privy embedded owner; request bodies cannot select it. External wallets retain direct gas payment. Both modes keep exact canonical owner action reconstruction and the fingerprint.

Call `assertPlanUsable` before recording wallet start. It checks the plan's time and actual network, then the Solana block-height boundary and blockhash validity, plus a fresh unsigned simulation. Sponsored Solana plans may defer only a pre-execution fee-payer balance/account error to Privy’s mandatory simulation; actual instruction failures, including rent funding, still fail. EVM sponsored plans retain route checks and exact owner calldata simulation without requiring owner ETH. EVM actions recheck their sealed route and simulate the exact owner payload. A failed RPC or expired unsigned plan leaves it refreshable before the wallet is opened. After any wallet attempt, preserve and reconcile its original hash; a timeout, missing historical metadata or an unobserved expired signature is `pending`/`attention`, not proof of failure.

EVM reconciliation requires the exact transaction envelope, canonical receipt block and time, and at least two blocks of confirmation before either success or failure is terminal. Successful financial receipts additionally require the exact canonical USDC transfer/approval. Direct Solana reconciliation compares the exact message and owner fee payer. Sponsored Solana recompiles the original instructions with the replacement fee payer/blockhash, preserving owner signing and all instruction data/accounts. A single leading sponsor-to-owner rent transfer may fund only the confirmed canonical account-creation rent or its funding deficit; payer debit must equal grant plus fee. Resolved account permissions and instruction bytes remain identical despite static account-table reordering. Implicit owner writability from the former fee payer may be narrowed. It then verifies the original receipt's USDC pre/post balance conservation. Verified failures must still belong to the original plan. Sponsored EVM receipts decode exactly one matching owner operation, require one canonical call, a paymaster or a third-party zero-price bundler whose actual owner-operation gas cost is zero, and the operation event/hash at the canonical receipt block, and isolate that operation’s logs. Successful outer bundles do not prove successful inner operations. Unsupported account/envelope formats fail closed. The repository enforces one terminal direct receipt per `(network, transactionHash)` and one terminal sponsored receipt per `(network, userOperationHash)`; failed attempts must not let foreign hashes squat on another user's receipt.

Snapshots read current owner-scoped vaults and the coordinator account. Preparation requires fresh authenticated reports that match the selected vaults' actual balances and cash-only readiness. Portfolio totals and database metadata never unlock a goal. Achievement remains permanent after claims and zero-balance progress; the progress helper uses its committed achieved total to retain a completed model.

Optional server RPC settings are `SOLANA_DEVNET_RPC_URL`, `BASE_SEPOLIA_RPC_URL`, `ARBITRUM_SEPOLIA_RPC_URL` and `ETHEREUM_SEPOLIA_RPC_URL`. They remain server-side and never enter unsigned plans. Public testnet RPCs are the fallback. API handlers should return unavailable state and block new wallet operations when a fresh snapshot cannot be verified.

`NABUNGFI_TESTNET_GAS_SPONSORSHIP=true` enables new sponsored plans only on the four hardcoded testnets. Privy dashboard must enable those chains, TEE execution, and client sponsorship. Old unsigned plans can be explicitly refreshed; attempted plans keep their original mode and outcome. Sponsored Solana blockhash replacement makes original-unsigned-lifetime negative proof unsafe, so that recovery requires the original actual signature. No fallback silently charges the user when sponsorship fails. Custom-program Solana account rent is separate from the network fee and is not promised sponsored. No app secret is exposed to the browser; signing remains in the user wallet.
