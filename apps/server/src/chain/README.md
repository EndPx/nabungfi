# Chain adapter boundary

`index.ts` exports `deriveGoalBinding`, `createChainService`, `planGoalStep`, `assertPlanUsable`, `readGoalState` and `reconcileGoalStep`. The module is read-only: it does not import wallet keys, sign, submit transactions, or write application metadata. `ReadOnlyRpc` refuses broadcast methods. The API repository owns authentication, durable step IDs, the original transaction hash and receipt uniqueness.

Provisioning uses a server-reserved random goal ID and verified linked wallet addresses. `deriveGoalBinding` derives the Solana goal/cash PDAs and canonical participants. Solana plus one to three supported EVM testnets is required. Each user signs `create-vault` on the selected EVM networks. The verifier discovers the **actual** vault from the canonical router's `VaultCreated` event and checks its independent configuration leaf and immutable provenance. It never reserves a predicted CREATE address. Only after all selected creation receipts are verified can the user sign Solana `initialize`.

The operator may coordinate authenticated registration, reports, readiness and commitment. User funds cannot deposit until every selected participant is registered and linked. User preparation and abort remain owner-signed Solana actions. EVM approval is a separate exact-amount step. Deposits and claims are never operator actions. The permissionless worker and its admission/fee policy live under `contracts/keeper`; this adapter does not grant it wallet ownership. The current operator registry has a finite capacity and must admit a new goal before promising coordination.

Every plan has a canonical JSON fingerprint that survives PostgreSQL JSONB key ordering. The verifier also reconstructs the canonical method/program/accounts, so a recomputed fingerprint cannot turn another instruction into an authorized goal action. Solana plans contain an unsigned v0 wire with zero signatures; direct signing wallets must preserve its exact message. EVM transaction plans are intended for direct owner EOAs. ERC-4337 bundler envelopes require a separate owner-operation verifier and are not silently accepted as direct-owner receipts.

Call `assertPlanUsable` before recording wallet start. It checks the plan's time and actual network, then the Solana block-height boundary and blockhash validity, plus a fresh unsigned simulation. EVM actions recheck their sealed route and simulate the exact owner payload. A failed RPC or expired unsigned plan leaves it refreshable before the wallet is opened. After any wallet attempt, preserve and reconcile its original hash; a timeout, missing historical metadata or an unobserved expired signature is `pending`/`attention`, not proof of failure.

EVM reconciliation requires the exact transaction envelope, canonical receipt block and time, and at least two blocks of confirmation before either success or failure is terminal. Successful financial receipts additionally require the exact canonical USDC transfer/approval. Solana reconciliation compares the exact message and owner fee payer, then verifies the original receipt's USDC pre/post balance conservation. Verified failures must still belong to the original plan. The repository must enforce one terminal receipt per `(network, transactionHash)`; failed attempts must not let foreign hashes squat on another user's receipt.

Snapshots read current owner-scoped vaults and the coordinator account. Preparation requires fresh authenticated reports that match the selected vaults' actual balances and cash-only readiness. Portfolio totals and database metadata never unlock a goal. Achievement remains permanent after claims and zero-balance progress; the progress helper uses its committed achieved total to retain a completed model.

Optional server RPC settings are `SOLANA_DEVNET_RPC_URL`, `BASE_SEPOLIA_RPC_URL`, `ARBITRUM_SEPOLIA_RPC_URL` and `ETHEREUM_SEPOLIA_RPC_URL`. They remain server-side and never enter unsigned plans. Public testnet RPCs are the fallback. API handlers should return unavailable state and block new wallet operations when a fresh snapshot cannot be verified.
